## Review of 0.14 changes (read-only)

I read AGENTS.md, README.md, and the seven listed files. Below are concrete, file-cited findings, ordered by your stated priority (controls → tattoo feedback → visual quality), followed by a note on what the 281 passing campaign checks actually prove for these claims.

### 1. Controls — input buffer, pause/hitstop/room reset

**Bug: mouse-based Light attack fires when clicking HUD chrome buttons during live combat.**
`Fighters.cs:163` reads raw `Input.GetMouseButtonDown(0)` every frame whenever `phase==Combat && !paused && !choice.HasValue`, with no check for whether the pointer is over a GUI element. `CampaignHUD.cs:98-99` always renders the "소지품 / I" and "기록 / 메뉴" buttons during combat (`controls` is true whenever there's no `choice` and phase isn't Death/Victory — this includes active dungeon combat, confirmed reachable by `CampaignSmokeTest.cs:434`, where `D.Open(VillagePanel.Inventory)` is exercised while `phase==Combat`). `Training.cs`'s "훈련 나가기" button (`CampaignHUD.cs:66`) has the same exposure during the training combat segment.

Unity's `OnGUI`/`GUI.Button` click registration does not suppress `Input.GetMouseButtonDown(0)`, and `Update()` (which queues the attack) runs before `OnGUI()` in the same frame. So the moment a player left-clicks the inventory/journal/exit-training button mid-fight, a stray Light attack is queued/executed on the mouse-down frame, before the panel-open even takes effect. This is a reproducible "unintended action" from the input buffer path, not a feel issue.
*Fix direction:* gate the mouse reads in `Fighters.cs:163-166` behind a check that the pointer isn't over an active HUD button rect (e.g. a frame-scoped static flag set by `CampaignHUD.Button()` when it draws an enabled button under the current mouse position), or stop binding combat Light attack to raw mouse button 0 at all.

**Confirmed correct by direct test evidence (not just inference):** buffer retains latest input, expires at .15s, hitstop preserves it, pause/accepted-hit/`ClearDelayedAttacks()` clear it, and parry→dash immediate transition is preserved. These are directly exercised at `CampaignSmokeTest.cs:587-610`.

**Missing evidence, not a proven bug:** AGENTS.md/README claim "room cleanup... clear them" for the input buffer. The smoke test only verifies this by calling `Barbarian.ClearDelayedAttacks()` directly (`CampaignSmokeTest.cs:604-605`), not by calling the actual `CampaignDirector.LoadRoom()`/`Travel()` path with a buffered input pending. `CampaignDirector.cs` is not among the reviewed files, so I can't confirm the real room-transition code path actually calls this clear — flag as unverified, not as a bug.

**Minor, debatable (display wording, not functionally wrong):** `CampaignHUD.CombatStatus` (`CampaignHUD.cs:117-129`) is called separately for Heavy/Parry/Dash (`CampaignHUD.cs:93-95`). When `player.Attacking` is true, it returns the same "준비 X초" / "후딜 X초" text under *all three* labels, including "F ·" and "SHIFT ·". That vocabulary ("준비"=windup, "후딜"=recovery) is attack-specific; parry and dash don't have those phases themselves. The information conveyed ("blocked because you're mid-attack") is accurate, but the specific terms displayed under the Parry/Dash rows could read as if parry/dash themselves have a windup/recovery state. This is a wording ambiguity, not a state-truthfulness bug — I note it but don't treat it as proven defect.

### 2. Tattoo feedback

I did not find a concrete bug in `TattooCombatEffects.cs`. `StateHint`'s read-only contract holds (no charge/timer mutation), the 7 switch-cased powers match the "7 tattoos get live state text" claim in README's 0.14 note, and severe-injury silencing is consistently gated through `G.body.Has(power)` at the top of `StateHint`. I did not have evidence (no access to `TattooCatalog.cs`) to verify the "8개 문신" count claimed in the changelog screenshot description, so I can't confirm or deny that specific number — flagging as unverifiable from the files given, not as a bug.

### 3. Visual quality — crate/vault semantics, display truthfulness, sprite lifetime

**Bug: README/AGENTS.md 0.14 text is false relative to the shipped code for the sealed vault.**
README states: "봉인 보급함·압력판은 아직 기존 도형입니다" (the sealed supply vault *and* pressure plate still use the old plain shapes). But `PressureTrial.cs:70` (`BuildVault()`) calls `PaintedCrateVisual.Attach(t,1f,12)`, which loads the same `Art/SupplyCrate-v1` texture used for the breakable/pushable crate (`PressureTrial.cs:51`). `Design/crate-art-provenance.json:19-23` explicitly lists "PressureTrial supply vault at 1.0 world height with separate state seal" as one of three intended uses of that asset — so this isn't an accidental fallback, it's documented as deliberate, yet contradicts the top-level changelog claim. Only the pressure plate itself (`BuildPlate()`, `PressureTrial.cs:58-64`) is actually still the old plain shape; the vault is not.
This also creates a real semantic-legibility risk: the destructible loot crate, the pushable/liftable puzzle crate, and the fixed, non-interactable-by-attack vault now all render as the same wooden/iron box silhouette (differing only in scale), even though their interaction rules are entirely different (breakable vs. pushable/liftable vs. fixed-open-by-E-only). *Fix:* either update the README/AGENTS.md claim to match actual behavior, or give the vault a visually distinct sprite/treatment so players don't expect to push or break it.

**Gap: corpse/"remains" weights have no proximity HUD hint at all.**
`PressureTrial.cs:37` exposes `RemainsCount`, and `TryLift()` (`PressureTrial.cs:152-171`) treats `remains` entries as liftable weights exactly like the crate. But `CampaignHUD.WorldLabels()` (`CampaignHUD.cs:156-171`) only computes `crateDistance` from `trial.CrateX` to decide whether to show the "운반 상자 · G 들기" prompt — it never checks proximity to any corpse in `remains`. `RemainsCount` is not referenced anywhere in `CampaignHUD.cs`. A player standing next to a corpse weight (but far from the crate) gets zero affordance hint, even though G will lift it. This is a concrete, demonstrable gap in the "상자 용도 안내" feature the 0.14 notes claim to have shipped, not a subjective quality judgment.

**No bug found in sprite lifetime:** `PaintedCrateVisual.OnDestroy` (`PaintedCrateVisual.cs:21`) destroys only its own owned `Sprite`, consistent with the stated contract. `PressureTrial`'s manually-created "Fallen draugr" sprite (`PressureTrial.cs:109-117`) is explicitly destroyed in both the pruning path (`DestroyRemainsVisual` → `DestroyRemainsSprite`, `PressureTrial.cs:96-101`) and in `OnDestroy()` (`PressureTrial.cs:276-280`) before the GameObject cascade-destroys. I did not find a leak path in the files reviewed, though I could not check `BreakableCache`/`CampaignDirector` (not provided) for their own crate-sprite cleanup.

### Test-coverage caveat
The 281 campaign checks and 21 combat checks are real scene/behavior-method tests (confirmed by reading `CampaignSmokeTest.cs` in full), and they do directly exercise most of the input-buffer claims (expiry, hitstop, pause-clear, accepted-hit-clear, parry→dash) and most PressureTrial claims (crate push/lift/throw, corpse weight reuse, room-transition teardown, pause freezing carried/flying props). They do **not** exercise: mouse-button input overlapping GUI buttons, the vault's actual rendered sprite, or a real `CampaignDirector.LoadRoom()` call with a pending buffered input. Passing tests are not evidence against the three bugs above, since none of those three paths are under test.

I have not modified any files. This review does not establish that the overall 0.14 goal (control feel validated) is complete — the mouse/GUI overlap bug above is a genuine control-feel defect that current automated tests cannot catch, and two documentation/display-truthfulness items need correction or author follow-up.
