## Summary of changes to `Assets/Scripts/PaintedCombatVisual.cs`

**New fields**: `ownedSprites` (tracking list), `originalSprite`, `walkFrames[6]`, `hasWalkCycle`, `walking`, `walkAnchorX`, `walkDistance`, `walkFrame`.

**New public read-only properties**: `HasWalkCycle`, `WalkFrame` (-1 when not walking).

**`Initialize`**:
- Idle sprite and axe blade sprite are now captured into `ownedSprites` for cleanup; idle sprite is also stored as `originalSprite` (the existing idle/combat fallback, unchanged).
- Hero-only: loads `Resources/Art/BarbarianWalk-v1`. If present, slices it into 6 cells (3 cols × 2 rows, cell = `width/3 × height/2`), reading left→right, top row then bottom row (`row = i<3 ? 1 : 0` since Unity rects are bottom-left origin). Each frame uses pivot `(.5, .08)` and PPU `cellHeight*.84/2.18`, matching the spec's padding/body-height math. Sets `hasWalkCycle=true` only if the texture loaded; otherwise everything behaves exactly as before (fallback preserved).

**New `OnDestroy`**: destroys every sprite in `ownedSprites` (idle, axe, 6 walk frames). Never touches the source `Texture2D` assets.

**New `UpdateWalkCycle` (called at the end of `LateUpdate`, only when not frozen)**:
- Walk eligibility: hero only, `Grounded && !Attacking && !Parrying && !Dodging && !Holding && !Headbutting && |velocity.x| > .1`.
- On entering walking, anchors `walkAnchorX` to current X and zeroes `walkDistance` (resume resets the anchor, no stride jump).
- Each frame, the raw per-frame X delta is checked against the teleport guard (`>2` units) — if tripped, the anchor still snaps forward but the distance isn't added, so a teleport can't inject a huge stride.
- Progress accumulates as `frameMove * facing`, so backpedaling (velocity opposite facing) drives the accumulator in reverse, naturally reversing frame order. One full 6-frame cycle = 2 world units (`cyclePos = (walkDistance/2) mod 1`).
- Leaving walking state restores `painting.sprite = originalSprite` and sets `WalkFrame = -1`.
- Because `LateUpdate` already early-returns when `Game.I.Frozen`, a freeze leaves the sprite/frame completely untouched, as required.

No changes to combat logic, `Fighters.cs`, or enemy behavior — only this file was touched.

**Concerns for the root/coordinator:**
1. I couldn't verify the actual pixel content of `BarbarianWalk-v1` (it's still being generated by Codex) — the slicing math assumes a perfectly even 3×2 grid with no extra border/margin outside the described padding. If Codex's sheet has any outer margin, frames will be mis-cropped.
2. No Unity editor/runtime available to me to test-play; this needs the described runtime capture step to confirm visually (gait looks right, no sprite flicker on state transitions).
3. `walkFrame` stepping is purely distance-driven with no smoothing/hysteresis at the exact 0/1 cycle boundary — a brief direction change right at a cycle edge can cause a 1-frame snap backward, which seemed acceptable per spec but worth a visual check.
